# Process Tracker — контракт

Нормативный контракт поведения. Реализация и README должны ему соответствовать.

## Идентичность и хранение

- История процессов независима для каждого Telegram `from.id`, вне зависимости от чата.
- История не удаляется командами бота.
- Все timestamps хранятся как Unix time в миллисекундах; отображение дат — UTC.
- Состояния процесса: `running`, `paused`, `stopped`.
- Активное время — сумма только интервалов `started_at..ended_at`; открытый интервал заканчивается в момент запроса.
- Приостановка закрывает текущий интервал. Возобновление создаёт новый интервал.

## Команды

### `/go "название" описание`

`Event: /go` → приостановить текущий `running`-процесс, если он есть → добавить его в стек паузы → создать новый процесс `running` и его открытый интервал → записать новый `active_process_id`.

Название обязательно. Описание необязательно. Новому процессу присваивается следующий `created_seq`.

### `/stop`

`Event: /stop` → если активного процесса нет, сообщить об этом без изменения данных. Иначе закрыть его открытый интервал, перевести его в `stopped`, записать `ended_at` → извлечь последний ID из стека паузы (LIFO), если он есть → возобновить этот процесс и создать новый открытый интервал → обновить `active_process_id`.

### `/what`

Выдать сводку:

- количество завершённых процессов и суммарное активное время;
- список приостановленных процессов с названием, активным временем и временем первого старта;
- для самого раннего первого старта среди приостановленных — время старта и время, прошедшее с него;
- последний актуальный процесс: название, первый старт, активное время, состояние и конец. Для `running`/`paused` конец отображается как `running` согласно текущему формату команды.

**Выбор `latest`:** первым должен идти процесс, чей ID равен `user_state.active_process_id`. Остальные сортируются по последней активности: максимум `COALESCE(intervals.ended_at, intervals.started_at)`, затем `processes.ended_at`, затем `processes.started_at`, затем `created_seq`. Выбор выполняется запросом к `processes p` с `SELECT p.*` и подзапросом к `user_state` по `user_id`.

Отчётный диапазон по умолчанию — от начала истории до момента запроса. При заданных границах длительности считаются по пересечению интервалов с `[from, to]`; timestamps — миллисекунды UTC.

### `/all`

Выдать все процессы по порядку создания. Для каждого показать название, состояние, время первого старта и время окончания; если окончания нет, вывести `null`/пустое значение согласно формату ответа. Даты — UTC.

### `/veryall`

Выдать все данные каждого процесса: название, ID, состояние, время первого старта, время окончания, описание, теги из `metadata.tags`, все метаданные JSON и полный список интервалов активности с началом и концом. Открытый интервал имеет конец `null`.

Длинные ответы разбиваются на несколько сообщений Telegram, не превышающих лимит безопасной длины.

## Контракт библиотеки

- `start(input)` → `ProcessRecord`; создаёт новый процесс и интервал, предыдущий активный процесс приостанавливает.
- `stop(userId, at?)` → остановленный `ProcessRecord` или `null`; после остановки возобновляет последний приостановленный процесс.
- `report(userId, range?)` → сводка `Report`, включая `latest` согласно правилу выше.
- `all(userId)` → все `ProcessSummary`, включая все интервалы.

## Схема состояний

`/go`: `running A → paused A + running B`

`/stop`: `running B + paused A → stopped B + running A`

Если стек паузы пуст: `/stop` переводит текущий процесс в `stopped`, активного процесса больше нет.
